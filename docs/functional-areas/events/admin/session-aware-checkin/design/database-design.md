# Database Design: Session-Aware Check-In System

**Feature**: Session-Aware Check-In
**Date**: 2025-11-30
**Designer**: database-designer agent
**Status**: Design Complete - Ready for Implementation

---

## Overview

This design converts the check-in system from event-scoped to session-scoped granularity, enabling:
- Multi-day event check-ins (Day 1, Day 2, etc.)
- Weekend pass holders can check into each session separately
- Single-day ticket holders restricted to their specific session
- Kiosk tokens scoped to specific sessions for security

### Current Architecture
- **CheckIn**: One check-in per attendee per EVENT (unique constraint on EventAttendeeId)
- **CheckInSessionToken**: Token grants access to entire EVENT
- **Business Logic**: No session-level validation

### Target Architecture
- **CheckIn**: One check-in per attendee per SESSION (unique constraint on EventAttendeeId + SessionId)
- **CheckInSessionToken**: Token grants access to specific SESSION only
- **Business Logic**: Session-level validation with ticket type checking

```csharp
/// <summary>
/// Session token for kiosk mode check-in access
/// Tokens are generated by admins and allow check-in operations without user authentication
///
/// CRITICAL: This is NOT user authentication - tokens provide scoped access to specific sessions
/// Pattern: Admin generates token → Opens on kiosk device → Volunteers use without login
/// </summary>
public class CheckInSessionToken
{
    /// <summary>
    /// Unique identifier for the session token
    /// </summary>
    public Guid Id { get; set; }

    /// <summary>
    /// Cryptographically secure token string (64 characters, URL-safe base64)
    /// Used in URLs and API headers for kiosk authentication
    /// </summary>
    [Required]
    [MaxLength(64)]
    public string Token { get; set; } = string.Empty;

    /// <summary>
    /// Event this token grants access to
    /// Tokens are scoped to a single event for security
    /// </summary>
    public Guid EventId { get; set; }

    /// <summary>
    /// Specific session this token grants check-in access to (REQUIRED)
    /// Ensures kiosk can only check in attendees to one session at a time
    /// For multi-day events, admins generate separate tokens per day
    /// </summary>
    public Guid SessionId { get; set; }  // ← NEW PROPERTY

    /// <summary>
    /// Admin user who generated this token
    /// Used for audit trail and security investigation
    /// </summary>
    public Guid CreatedByUserId { get; set; }

    /// <summary>
    /// When the token was generated (UTC)
    /// </summary>
    public DateTime CreatedAt { get; set; }

    /// <summary>
    /// When the token expires (default: 12 hours after creation)
    /// After expiration, token is automatically invalid
    /// </summary>
    public DateTime ExpiresAt { get; set; }

    /// <summary>
    /// Whether the token has been manually revoked by an admin
    /// Used for emergency revocation if device is lost/compromised
    /// </summary>
    public bool IsRevoked { get; set; }

    /// <summary>
    /// When the token was revoked (if applicable)
    /// </summary>
    public DateTime? RevokedAt { get; set; }

    /// <summary>
    /// Admin user who revoked this token (if applicable)
    /// </summary>
    public Guid? RevokedByUserId { get; set; }

    /// <summary>
    /// Last time this token was used for a check-in operation
    /// Updated on every check-in API call for monitoring
    /// </summary>
    public DateTime? LastUsedAt { get; set; }

    // Navigation properties
    public Event? Event { get; set; }
    public Session? Session { get; set; }  // ← NEW NAVIGATION PROPERTY

    /// <summary>
    /// Constructor initializes required fields
    /// </summary>
    public CheckInSessionToken()
    {
        Id = Guid.NewGuid();
        CreatedAt = DateTime.UtcNow;
        IsRevoked = false;
    }
}
```

## Index Recommendations

### Performance Optimization Strategy

#### CheckIns Table Indexes

1. **IX_CheckIns_SessionId** (Single Column)
   - **Purpose**: Fast session-scoped check-in queries
   - **Query Pattern**: `WHERE SessionId = @sessionId`
   - **Cardinality**: Low (few sessions per event)

2. **IX_CheckIns_Session_Time** (Composite)
   - **Purpose**: Check-in timeline queries per session
   - **Query Pattern**: `WHERE SessionId = @sessionId ORDER BY CheckInTime`
   - **Cardinality**: Medium (hundreds of check-ins per session)

3. **UQ_CheckIns_EventAttendee_Session** (Unique Composite)
   - **Purpose**: Enforce one check-in per attendee per session
   - **Query Pattern**: `WHERE EventAttendeeId = @attendeeId AND SessionId = @sessionId`
   - **Cardinality**: High (unique pairs)

#### CheckInSessionTokens Table Indexes

1. **IX_CheckInSessionTokens_SessionId** (Single Column)
   - **Purpose**: Session token lookups
   - **Query Pattern**: `WHERE SessionId = @sessionId`
   - **Cardinality**: Very Low (1-3 tokens per session)

2. **IX_CheckInSessionTokens_SessionId_ExpiresAt_Active** (Partial Composite)
   - **Purpose**: Active token validation per session
   - **Query Pattern**: `WHERE SessionId = @sessionId AND IsRevoked = false AND ExpiresAt > NOW()`
   - **Filter**: `WHERE IsRevoked = false` (partial index for performance)
   - **Cardinality**: Very Low (active tokens only)

### Index Size Estimates

**Assumptions**:
- 100 events/year
- Average 2 sessions per event
- Average 50 attendees per session
- 3 kiosk tokens per session

**CheckIns Table**:
- Records: ~10,000/year
- `IX_CheckIns_SessionId`: ~40 KB
- `IX_CheckIns_Session_Time`: ~80 KB
- `UQ_CheckIns_EventAttendee_Session`: ~120 KB

**CheckInSessionTokens Table**:
- Records: ~600/year
- `IX_CheckInSessionTokens_SessionId`: ~10 KB
- `IX_CheckInSessionTokens_SessionId_ExpiresAt_Active`: ~5 KB (partial)

**Total Additional Index Storage**: ~255 KB/year (negligible)

```csharp
public async Task<bool> CanCheckInToSession(Guid attendeeId, Guid sessionId)
{
    var attendee = await GetEventAttendeeAsync(attendeeId);
    var session = await GetSessionAsync(sessionId);

    // RSVP attendees (no ticket) can check into ANY session
    if (attendee.AttendanceType == AttendanceType.RSVP)
    {
        return true;
    }

    var ticketPurchase = await GetTicketPurchaseForAttendee(attendeeId);
    var ticketType = ticketPurchase.TicketType;

    // Multi-session ticket (SessionId == null) - can check into ANY session
    if (ticketType.SessionId == null)
    {
        return true;
    }

    // Single-session ticket - MUST match the session being checked into
    if (ticketType.SessionId == sessionId)
    {
        return true;
    }

    // Ticket doesn't grant access to this session
    return false;
}
```

#### Business Rule Summary

| Ticket Type | SessionId on TicketType | Can Check Into |
|-------------|-------------------------|----------------|
| Weekend Pass | `NULL` | Any session of the event |
| Day 1 Ticket | `<Session1_Id>` | Session 1 ONLY |
| Day 2 Ticket | `<Session2_Id>` | Session 2 ONLY |
| RSVP (Free) | N/A (no ticket) | Any session (honor system) |

## Data Migration Considerations

### Current System State

**User Confirmation**: No live data in production

### Migration Safety Patterns

Even with no live data, the migration follows safe patterns for future reference:

1. **Add Column as Nullable**
   - Allows existing records to remain valid during migration
   - Prevents constraint violations during schema changes

2. **Populate Data**
   - Uses SQL script to set SessionId to event's first session
   - Ensures all records have valid SessionId before constraint enforcement

3. **Make Column Required**
   - After data population, enforce NOT NULL constraint
   - Prevents future records from missing SessionId

4. **Add Foreign Keys**
   - Ensures referential integrity to Sessions table
   - Prevents orphaned check-ins

5. **Add Unique Constraint**
   - Changes from event-scoped to session-scoped uniqueness
   - Enables multi-session check-ins per attendee

### Rollback Strategy

The `Down()` method provides full rollback capability:

1. Drop new constraints and indexes
2. Remove foreign keys
3. Drop SessionId columns
4. Restore original unique constraint
5. Restore original indexes

**Testing Rollback**:
```bash
# Apply migration
dotnet ef database update

# Rollback migration
dotnet ef database update PreviousMigrationName
```

## Performance Considerations

### Query Performance Impact

#### Before (Event-Scoped)
```sql
-- Check if attendee already checked in
SELECT * FROM "CheckIns"
WHERE "EventAttendeeId" = @attendeeId;

-- Index used: UQ_CheckIns_EventAttendee
-- Query time: ~1ms
```

#### After (Session-Scoped)
```sql
-- Check if attendee already checked into THIS session
SELECT * FROM "CheckIns"
WHERE "EventAttendeeId" = @attendeeId
AND "SessionId" = @sessionId;

-- Index used: UQ_CheckIns_EventAttendee_Session
-- Query time: ~1ms (same performance)
```

**Result**: No performance degradation - unique composite index provides same O(1) lookup

### Token Validation Performance

#### Before
```sql
-- Get active tokens for event
SELECT * FROM "CheckInSessionTokens"
WHERE "EventId" = @eventId
AND "IsRevoked" = false
AND "ExpiresAt" > NOW();

-- Index used: IX_CheckInSessionTokens_EventId_ExpiresAt_Active
-- Query time: ~1ms
```

#### After
```sql
-- Get active tokens for specific session
SELECT * FROM "CheckInSessionTokens"
WHERE "SessionId" = @sessionId
AND "IsRevoked" = false
AND "ExpiresAt" > NOW();

-- Index used: IX_CheckInSessionTokens_SessionId_ExpiresAt_Active
-- Query time: ~1ms (same performance)
```

**Result**: No performance change - same partial index strategy, just different scope

### Storage Impact

- `SessionId` column: 16 bytes (UUID)
- CheckIns table: ~10,000 records/year × 16 bytes = 160 KB/year
- CheckInSessionTokens table: ~600 records/year × 16 bytes = 10 KB/year

**Index Storage**: ~255 KB/year (see Index Recommendations section)

**Total Annual Storage Impact**: ~425 KB/year (negligible)

- Previous system: 100 check-in records
- New system: 200 check-in records (100 per session)

**Storage Impact**: 200 records × 16 bytes = 3.2 KB additional storage per event

**Database Growth**: Linear with session count, not a concern for foreseeable future

## Security Considerations

### Token Scope Restriction

**Before**: Token grants access to entire EVENT
- Security Risk: Compromised token allows check-in to all sessions
- Use Case: Weekend event with Friday/Saturday/Sunday sessions

**After**: Token grants access to specific SESSION
- Security Improvement: Compromised token only affects ONE session
- Admin generates separate tokens per session (Friday token, Saturday token, Sunday token)

### Audit Trail

**No Changes Required**: Existing audit fields capture session-level granularity:
- `CheckIn.SessionId` - Which session was checked into
- `CheckIn.StaffMemberId` - Who performed the check-in
- `CheckIn.CreatedAt` - When check-in occurred
- `CheckInSessionToken.SessionId` - Which session the token grants access to

### Check Constraints

The database-level check constraints prevent:
- CheckIn with SessionId not belonging to EventId
- CheckInSessionToken with SessionId not belonging to EventId
- Data integrity violations from application bugs
